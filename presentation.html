Three agents, one structured LLM call

CodePraxis runs AI technical interviews and a developer learning product. Underneath, every agent turn is the same thing: one LLM call that reads a long structured prompt and returns one JSON move. That makes the whole product something we can replace, measure and fine-tune.

1The problem and the architecture

We run three agents. They look different to the user, but they share one engine, one calling convention and one output format.

Interview

Runs a live technical interview

Works through one question: a seed, then a chain of probes, with a clock. Decides what to say next and when to move on.

Moves: FOLLOW_UP · HINT · CLARIFY · REDIRECT · PROBE · QUESTION_DONE

Assess

Examines a learner, closed book

Walks a fixed chain of stages after study, grades each stage against a rubric. No clock, and it must never teach.

Same six moves. Closing a stage also sets level (strong / ok / weak) and evidence.

Study

Tutors a learner through a lesson

Explains, points at the lesson or a file, sets a try, checks understanding, writes to the learner's notes. Explaining is its job; handing over solutions is not.

Moves: EXPLAIN · POINT · TRY · CHECK_ME · REDIRECT · SUGGEST_ASSESS · ADD_NOTE

Why one call per turn matters

  • Every call is self-contained. The prompt already carries the question, stage, clocks, files and chat so far, so one logged turn is one training example. There is no conversation order to preserve.
  • The schema does the policing. A model cannot pick an illegal move, so the format is nearly free to learn. The hard part is judgement.
  • One interface. Claude, GPT, Fireworks-hosted models and local models all sit behind the same completer, so comparing them is a one-line change.

One turn, input and output

An invented example in the shape of a real Interview turn. The question, files and candidate are made up; the section names and the output shape are the real ones.

  "move": "HINT",
  "hint_id": 1,

Why this is a good answer

Right move for the clock: 52 seconds left and the last push did not land, so it spends a hint instead of probing again.

Responds to a Hinglish, wrong-but-confident message without correcting the candidate's English.

Reveals nothing withheld: it points at line 14 and the loop condition, but does not mention a step budget or that the error text re-enters the prompt.

Private vs shown: only response reaches the candidate. gap and note are the interviewer's records.

What we wanted to do with it

Run this on Claude Opus for a 50,000-student, two-day screening round and the model bill is roughly $50–90K. Run it on an open 9B model we host ourselves, trained to make the same decisions, and it is roughly $1–3K. The question is whether a small open model can make these judgement calls well enough. Sections 2 and 3 answer that.

2The baseline

Before training anything, we measured where an untrained 9B stands against the frontier, on turns it has never seen, with the real engine.

How the test set covers every direction

  • Every field of the prompt is varied: clocks, depth, hints left, probe options, the set of moves offered, history length, files (code, repo, image, PDF, video, drawings), code-run results, Learn notes, gaps and memory.
  • Candidates: strong, partial, confidently wrong, "I don't know", fishing for the answer, off-topic, prompt injection, terse, code-pasting, slow; written clean, with typos, SMS spelling, dictation fillers, or in Hinglish.
  • Held out: 2–3 questions per track and 3 Learn sub-modules are never used for training, so the final score measures generalisation.

What the baseline tells us

The untrained 9B produces valid JSON 99% of the time, because the schema forces it. What it lacks is judgement: it gives answers away, skips ahead and explains them, gives in to answer-fishing, grades a third of stages differently from Opus, and changes its decision on messy English more than half the time.

Why this makes the plan work

An open model (DeepSeek V4.1 Flash) already matches Opus, inside Opus's confidence range in every mode, at about 14× lower cost. So we distil it into the 9B: train Qwen3.5-9B with LoRA on 9,043 judged-and-filtered teacher turns, then score it on the same test set.

The teacher was chosen from five open models (Kimi K3, Qwen 3.8 Max, DeepSeek V4.1 Flash, gpt-oss-120B, GLM 5.3) by a rule fixed before the results: the licence allows training on outputs, it gives answers away no more than Opus does plus 2 points, best quality wins, and the cheaper model wins on a tie. No Claude or GPT output is used as a training target.

3The evaluation

Each model answers the frozen test prompts. Code checks what code can check, and an AI judge reads each mode's own context for the rest. Opus is the reference throughout.

Code

Valid output

The reply parses, matches that turn's schema, is a move we offered, and uses real probe and hint ids.

Code

Same move · same grade

Does it make Opus's decision? For Assess, the same strong / ok / weak grade when both close a stage.

Code

Messy English

60 answers given clean and rewritten with typos, SMS spelling and fillers. The score is how often the move stays the same.

AI judge

Quality, 1–5

Per-mode criteria with a quoted line as evidence. The judge never penalises the candidate's grammar or Hinglish.

AI judge

Gives the answer away

Interview: spoon-feeding. Assess: teaching or revealing. Study: handing over a solution. Judged only against what the candidate actually reads.

AI judge

Head to head and safety

Opus's reply against the model's, in random order. And a safety check on answer-fishing and prompt-injection turns: stayed in role, revealed nothing, redirected.

Each mode's judge is shown that mode's own prompt sections: the rubric and withheld list for Assess, the files and reference solutions for Study. Assess has no clock, so "fits the clock" does not apply. A Study tutor is supposed to explain, so only handing over a solution counts as a leak.

We checked the judge against Opus, and fixed it

Opus is the ground truth, so a judge that marks Opus down is suspect. We read every Opus turn it flagged and found four bugs in the judge, not in the data:

BugWhat went wrongFix
Private fields read as leaksThe judge saw the whole move, including grades, evidence and notes that never reach the candidateIt sees candidate_reads apart from the private fields, and private fields can never leak
An invented rule"One question at a time" was applied to interviews, which have no such rule. It failed Opus on 49 of 100 turnsRemoved for interviews; kept for Assess, where the prompt requires it
Stage set-up counted as a leakWhen a stage closes, the next stage's authored scenario legitimately describes what the team didA leak counts only while its stage is open; the judge is told on each closing move, and code enforces it
Invented quotesThe judge sometimes quoted text that was not in the replyA "gave the answer away" verdict must quote real text from the reply, checked in code, or it is discarded

After the fixes

Opus scores 4.63 / 4.63 / 4.30 (Interview / Assess / Study) on a validation run, and base Qwen scores 3.53 / 2.57 / 3.43. Opus's remaining mark-downs are real slips: two questions in one Assess turn, a reply cut off at the output limit, and a small exercise step handed over in Study.

How to read the numbers

Every rate has a 95% bootstrap interval, and comparisons use the same 300 turns for every model. The judge is one model (GPT-5.4) and strict, so the ranking between models is more reliable than any absolute value. It is not yet calibrated against human labels; that is our main open limit.

What comes next

  1. Fine-tune Qwen3.5-9B with LoRA on the filtered teacher data (8,361 train and 682 validation examples, split by session).
  2. Deploy it and run it on the same 1,525 test turns, judged by the same judge.
  3. Report quality against cost and latency, with Opus and the untrained 9B as the two reference points.
